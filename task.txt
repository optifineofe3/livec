У тебя есть полный исходный код проекта LiveContainer.

Нужно настроить GitHub Actions / build так, чтобы получить именно ВТОРОЙ LiveContainer, который предусмотрен самим проектом как `LiveContainer2`, а НЕ отдельную переписанную версию и НЕ просто переименованный основной LiveContainer.

Изучи исходники перед изменениями, особенно:
- `LiveContainerSwiftUI/Utilities/LCUtils.m`
- метод `archiveIPAWithBundleName:`
- `LiveContainerSwiftUI/Views/Settings/LCMultiLCManagementView.swift`
- `LCSharedUtils.m`
- текущие GitHub Actions workflows / `.yml`
- `Assets.xcassets`
- `Info.plist` и все места, где задаются bundle display name, bundle identifier, URL schemes и AppIcon.

Цель:

1. Собрать обычный LiveContainer штатным способом.
2. Использовать существующий механизм проекта, который создаёт `LiveContainer2` через `archiveIPAWithBundleName:@"LiveContainer2"`.
3. Получить IPA именно второго контейнера с:
   - Bundle Identifier: `com.kdt.LiveContainer2`
   - URL scheme: `livecontainer2`
   - внутренней идентичностью второго контейнера, которую ожидает сам LiveContainer.
4. На iPhone приложение второго контейнера должно отображаться под названием:
   `Books`
5. Для второго контейнера должна использоваться отдельная иконка Books.
6. НЕ ломать обычный `LiveContainer`.
7. НЕ менять его bundle identifier / URL scheme.
8. НЕ превращать `LiveContainer2` просто в новый независимый target, если существующий механизм проекта уже умеет генерировать второй контейнер.
9. Не дублировать исходники без необходимости.

Главный вопрос перед изменениями:
определи, КАК именно текущий `archiveIPAWithBundleName:` создаёт `LiveContainer2` и где в процессе генерации можно безопасно подменить только:
- `CFBundleDisplayName` / отображаемое имя на `Books`;
- App Icon на отдельную иконку Books.

Очень важно:
внутренние значения, необходимые для работы второго контейнера, должны остаться такими, какие ожидает LiveContainer:
- bundle identifier второго контейнера;
- `livecontainer2`;
- необходимые executable / scheme / идентификаторы.

То есть пользовательское имя `Books` НЕ должно случайно заменить `LiveContainer2` там, где `LiveContainer` использует это имя технически.

### Иконка

Сначала найди в проекте существующий механизм AppIcon и способ, которым `archiveIPAWithBundleName:` выбирает/меняет иконку.

Создай отдельный asset для второго контейнера, например:

`AppIconBooks`

или другое подходящее имя, если архитектура проекта требует иного.

Я положу исходные изображения иконки в то место, которое ты мне укажешь.

Нужно определить:
- какие размеры/scale нужны;
- какие файлы PNG нужны;
- куда именно их положить;
- нужно ли менять `Contents.json`;
- как сделать так, чтобы обычный LiveContainer продолжал использовать свою оригинальную иконку.

### GitHub Actions

Подрихтуй существующий workflow `.github/workflows/*.yml` минимально необходимым образом.

Мне нужен workflow, который после билда выдаёт готовый IPA именно второго контейнера.

Не создавай ненужную новую архитектуру проекта.

Если текущий workflow уже умеет собирать LiveContainer и потом создавать IPA через существующий скрипт/код, используй этот механизм.

Если `archiveIPAWithBundleName:@"LiveContainer2"` вызывается только из runtime и GitHub Actions не может напрямую получить созданный им IPA, найди наиболее близкий существующий проектный механизм и сделай минимальное изменение, позволяющее получить тот же результат в CI.

При этом НЕ подменяй `LiveContainer2` на обычный `LiveContainer` с другим именем.
